# Portable agent architecture and support policy

This guide helps build reusable agents across providers, frameworks, services, and
deployment targets without claiming that every combination is supported by the
scaffolder. Separate the user-facing design from the framework-specific implementation.

## Support levels

Every provider, framework, and integration must be labeled with one of these levels:

- **Scaffolded**: generated by this skill's scaffold, and the generated project passes
  `audit.py` (once placeholders are replaced) and its offline tests. CI generates and tests
  every scaffolded pattern on each push (`.github/workflows/ci.yml`).
- **Recipe**: implementation guidance exists, but the scaffold and contract tests do
  not cover it. Validate APIs and run the user's tests before calling it done.
- **Experimental**: an option under evaluation; disclose missing tests and known gaps.
- **Unsupported**: do not generate implementation code for it. Offer an architecture
  recommendation or ask to choose a supported alternative.

Never infer support from a package name in a reference list. Record the version range,
test date, and capability gaps for every scaffolded combination. Prefer a small matrix
of tested combinations over an unbounded provider × framework × service matrix.

## Decisions to capture

Put these choices in `design/architecture.md`, with rationale and alternatives:

1. **Provider and model**: provider, exact model/deployment ID, region or hosting route,
   structured-output/tool-use support, context limits, data-retention constraints, and
   expected cost. Pin model IDs; do not silently select a moving alias.
2. **Runtime/framework**: framework and version, why it fits the control-flow needs,
   how sessions/state are managed, and which capabilities are provider-specific.
3. **Tools and protocols**: native function tools, MCP, REST/OpenAPI, browser automation,
   or bounded local capabilities. Name each tool, its data access, read/write effects,
   timeout, retry/idempotency behavior, and approval requirement.
4. **Services**: identify only required services, their auth method and least-privilege
   scopes, data exchanged, failure behavior, and whether a local/mock implementation
   is available for tests.
5. **State and memory**: what is per-turn, per-session, durable, or shared; retention and
   deletion rules; tenant isolation; and recovery after process restart.
6. **Delivery and operations**: CLI, library, API, worker, or deployment target; health
   checks, logs/traces, alerting, rollback, and ownership of secrets.
7. **Budgets and risks**: latency and spend limits, expected volume, cost of errors,
   human approval points, and explicitly accepted open risks.

Include a component diagram and at least one sequence showing a failure or
side-effecting action. If a choice is not yet known, record the assumption and its
impact instead of silently choosing a service or framework.

## Adapter contract

Provider and framework adapters should expose or document equivalent behavior for:

- invoking a pinned model and reporting request IDs, usage, latency, and errors;
- bounded turns, timeouts, concurrency, and spend where the runtime supports them;
- typed/validated output and explicit handling of refusal, truncation, and tool calls;
- tool registration with least privilege and policy checks before side effects;
- per-user/per-session state boundaries and cancellation;
- transient-only retries, with no automatic retry of permanent client errors;
- tracing and eval hooks that do not log secrets or raw sensitive payloads by default.

Do not hide important framework features behind a false common denominator. If an
adapter cannot provide a capability, document the gap in the architecture and either
select another stack or obtain approval for the risk.

## Tool and integration policy

Treat every tool/service as an independent trust boundary, including MCP servers.
Classify tools as read-only, reversible write, irreversible/high impact, or privileged.
For each, define:

- input schema, authorization checks at the data-owning service, and minimal scopes;
- whether execution is automatic, requires confirmation, or is prohibited;
- timeout, rate limit, idempotency key, retry policy, and useful error result;
- audit event fields, with secrets and sensitive content excluded;
- mock/fake service behavior for unit and contract tests.

Use the lightest mechanism that satisfies the requirement. Prefer an in-process tool for
one application-specific capability; use MCP when standardized access must be reused
across clients; use a workflow/service integration when deterministic code is more
reliable than model-selected actions. Never treat prompt wording as authorization.

## End-to-end gates

1. **Requirements gate**: capture real input/output examples, measurable acceptance
   criteria, users, environment, budgets, data sensitivity, and forbidden actions.
2. **Tier gate**: compare single call, deterministic workflow, bounded agent, and
   hybrid. Explain why model-owned control flow adds enough value to justify its cost
   and failure modes.
3. **Architecture gate**: write and review the plan above before generating project
   code. Get explicit approval for providers, services, side effects, and deployment.
4. **Implementation gate**: scaffold only a supported combination; replace every
   placeholder tool, prompt, and sample eval with requirement-specific behavior.
5. **Verification gate**: run lint/type checks, unit tests without credentials,
   adapter contract tests, and representative/boundary/adversarial evals. Model-backed
   evals require cost disclosure and user approval. Do not count starter examples as
   evidence that user requirements pass.
6. **Readiness gate**: if production is in scope, verify packaging/CI, secret setup,
   health and failure behavior, monitoring, rollback, and operational documentation.
   If not run, mark each item as unverified.
7. **Handoff gate**: report commands, pinned versions, test/eval evidence, estimated
   operating cost, required credentials, known limitations, and remaining risks.

Static audits are heuristics, not security reviews or sandboxes. For high-impact
actions, enforce authorization and approval in code and at the service that owns the
data. Explain the boundary of each check in the handoff.
